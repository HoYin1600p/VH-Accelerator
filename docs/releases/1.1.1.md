# VH Accelerator 1.1.1 — critical fix

Version 1.1.1 fixes two problems in 1.1.0: blocks that could render invisible,
and vault portals that could fail to take the player in. Everyone on 1.1.0
should update.

## Download and compatibility

The release artifact is `VH-Accelerator-1.1.1.jar` for Minecraft 1.18.2 and
Forge 40.3.11 or later in the Forge 40.x line. Compatibility is unchanged from
[1.1.0](1.1.0.md). Do not install a sources JAR.

## Fixed

- Opening a new vault could leave the player standing in the portal, never
  teleported in, with no error (`snapshotVaultEventListeners`). Vault Hunters'
  Forge-backed events, including its server tick, add listeners directly to
  the event's listener table, bypassing the registration method VH Accelerator
  monitored. VH Accelerator's cached listener list therefore never included
  the new vault's tick, which performs the teleport. Those registrations now
  refresh the cached list, and every event also checks that the table has not
  grown. Relogging used to release stuck vaults, which could then pull the
  player back and forth between them; that can no longer happen. The same gap
  could skip listeners that cake-vault modifiers add during a vault.
- Some block variants could render fully invisible (no geometry and no
  missing-model cube), for example sideways logs and pillars, and slabs of one
  type. It affected warm launches with `skipBlockStateGraphLoading` and
  `deferBlockStateModelBaking` enabled, the 1.1.0 defaults. When a block's
  models were first needed, only the requested variant's model files were
  loaded, and the block's other variants were then built without their parent
  model, which holds their shape. The first use now loads every variant of the
  block, as Minecraft's normal model loading does.

Players who worked around the problem by setting
`deferBlockStateModelBaking = false` can set it back to `true` after updating.
